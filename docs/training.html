1 — Ce que le modèle apprend et comment il est évalué

La question posée : un accident corporel fera-t-il au moins une victime grave (blessé hospitalisé ou tué) ? Classification binaire sur 27 variables (usager, véhicule, lieu, conditions, heure…) issues des 4 fichiers annuels ONISR — voir le Dictionnaire des données.

Split temporel : apprendre sur le passé, tester sur l'avenir

Les données de toutes les années disponibles sont cumulées. Le modèle apprend sur les années précédentes et il est évalué sur la plus récente, qu'il n'a jamais vue — exactement la situation de production, où il prédit des accidents futurs.

Exemple (cycle 2024)AnnéesLignes
Apprentissage2021 · 2022 · 2023~173 000
Test2024~65 000

Un split aléatoire mélangerait des accidents de la même année entre apprentissage et test et surestimerait la performance réelle.

Les 3 algorithmes comparés à chaque cycle
AlgorithmeNom dans MLflowPrincipe
Random Forestrf_accidentsDes centaines d'arbres indépendants qui votent — robuste, peu sensible au réglage.
XGBoostxgb_accidentsArbres construits l'un après l'autre, chacun corrige les erreurs du précédent.
LightGBMlgbm_accidentsMême principe que XGBoost, optimisé pour la vitesse et les grands volumes.

Les trois sont entraînés à chaque cycle, sur exactement les mêmes données : le choix du meilleur est refait à chaque fois, il n'est jamais figé.

Les 4 métriques
MétriqueCe qu'elle mesureSeuil minimum
F1 — métrique principaleÉquilibre entre précision et rappel sur la classe « grave »≥ 0,60
AUC ROCCapacité à classer un accident grave au-dessus d'un non grave (0,5 = hasard, 1 = parfait)≥ 0,77
Recall (rappel)Part des accidents réellement graves que le modèle détecte≥ 0,58
AccuracyPart de prédictions correctes, toutes classes confondues≥ 0,72

Les seuils sont fixés ~8 % sous les performances observées : ils écartent un modèle nettement dégradé sans bloquer une variation normale d'une année à l'autre.

2 — Comment le champion est choisi, et à quelles conditions il est promu
Trois filtres successifs (tâche Prefect select-champion) : ① passer les 4 seuils minimums → ② être le meilleur en F1 parmi les qualifiés → ③ faire mieux que le modèle en production, selon une règle qui dépend du déclencheur. Puis ④ un humain valide (GO).
① Les seuils minimums (quality gate)

Un modèle sous un seul des 4 seuils (F1 ≥ 0,60 · AUC ≥ 0,77 · Recall ≥ 0,58 · Accuracy ≥ 0,72) est éliminé, quel que soit son F1. Le run porte le tag MLflow kpi_gate=PASSED ou FAILED. Si aucun des 3 ne passe : pas de champion, la production reste inchangée et une alerte est émise.

② Le meilleur en F1

Parmi les modèles qualifiés, celui qui a le F1 le plus élevé devient le champion du cycle — les deux autres restent enregistrés dans MLflow pour comparaison.

③ Faire mieux que la production — règle selon le déclencheur
DéclencheurRèglePourquoi
Trigger 1 — nouvelle année de donnéesPromu si au plus 1 métrique sur 4 régresse par rapport à la production (2 ou plus → pas de promotion)Le nouveau modèle est testé sur une année plus récente que l'ancien : la comparaison stricte n'est pas équitable, mais une dégradation sur plusieurs métriques reste un signal fort.
Trigger 3 — nouveau blueprint (hyperparamètres)Promu si son F1 dépasse celui de la production d'au moins +0,01Mêmes données, même test : la comparaison est directe. Le +0,01 évite de remplacer un modèle pour une différence due au hasard.
Aucun modèle en production (premier cycle, après une remise à zéro)Le champion est promu directementRien à comparer.
Réentraînement complet (full-retrain, rejeu de l'historique)Seuils minimums seulementChaque année rejouée remplace la précédente, comme dans la vraie vie.
④ La validation humaine et la mise en production
  • Le champion n'est pas promu tout de suite : le flow deploy-vps-flow s'arrête à la gate, qui affiche dans le Cockpit ses métriques face à celles de la production.
  • GO → alias @Production déplacé vers le champion, redémarrage de l'API, tests fonctionnels ; si un test échoue → retour automatique au modèle précédent.
  • STOP → rien ne change ; le run est tagué gate_outcome=stopped (visible « Stoppé » dans le Cockpit).
Contrôle complémentaire : comparer les décisions (model diff)

Avant la gate, le champion et le modèle en production prédisent le même jeu de référence figé (issu des données 2021, jamais modifié). On mesure la part de décisions qui changent de classe. Informatif, jamais bloquant : au-delà de 20 % de décisions changées, le candidat mérite un examen attentif avant le GO. Rapport visible dans le Cockpit → Modèles.

3 — L'entraînement de production

Entièrement automatisé, exécuté par Prefect sur le VPS. Les runs vont dans l'expérience MLflow accidents_severity_prod et chaque modèle est enregistré dans le registre.

Qui le déclenche
DéclencheurQuandChaîne Prefect
Trigger 1 — nouvelles donnéesDétection chaque lundi à 8 h de la publication ONISR annuelle (en général à l'automne)check-new-data → ETL → train-flow → deploy-vps-flow (gate)
Trigger 3 — nouveau blueprintMerge sur main d'une PR qui modifie config/model_params.ymlCD → update-model-flow → train-flow → deploy-vps-flow (gate)
Réentraînement completÀ la main (Cockpit → Orchestration)full-retrain : rejoue tous les cycles annuels depuis zéro

Un changement de code (Trigger 2) ne réentraîne jamais le modèle.

Les étapes du flow train-flow
#Tâche PrefectCe qu'elle fait
1train-model-rf · -xgboost · -lgbmEntraîne chaque algorithme avec les hyperparamètres du blueprint, calcule les 4 métriques, enregistre le run et le modèle dans MLflow, produit le rapport de performance Evidently.
2get-metrics-…Relit les métriques de chaque run dans MLflow.
3select-championApplique les filtres ①②③ (section 2).
4write-performance-summaryPublie les métriques du champion pour Grafana (« F1 du dernier champion »).
5model-diffCompare les décisions du champion et de la production sur le jeu de référence.

Le flow ne promeut pas lui-même : il passe le champion à deploy-vps-flow, qui attend le GO.

Rapports produits à chaque entraînement
  • Rapport de performance (Evidently) par algorithme et par version : matrice de confusion, courbes ROC et précision-rappel sur l'année de test — Cockpit → Modèles → « Rapports par version ».
  • Rapport model diff champion vs production (section 2).
  • Tableau de comparaison à la production, affiché à la gate.
4 — L'entraînement de développement et le blueprint

Le Data Scientist explore en local, sans jamais toucher la production. Ses runs remontent dans le MLflow partagé, dans une expérience séparée (accidents_severity_dev). Quand il trouve de meilleurs hyperparamètres, il les propose via un blueprint. Détail des commandes : Guide Data Scientist.

Qu'est-ce que le blueprint ?

Le fichier config/model_params.yml : les hyperparamètres de référence des 3 algorithmes, versionnés dans Git. C'est lui que l'entraînement de production utilise, à chaque cycle. Le modifier est la seule façon de changer la façon dont la production entraîne ses modèles — et cela passe forcément par une PR relue.

Priorité à l'entraînement : option en ligne de commande (exploration DS) > blueprint > valeur par défaut de la librairie. Les paramètres techniques (random_state=42, n_jobs=-1, verbosité) sont imposés par le pipeline pour garantir la reproductibilité.

Le parcours du DS, de l'exploration à la production
#ÉtapeComment
1Préparer sa session./scripts/ds_session_start.sh : synchronise la branche DS et récupère les données (DVC).
2Explorerpython -m src.models.train_model --year 2024 --cumul --algorithm lgbm --num-leaves 127 … --no-register, ou recherche automatique (Grid Search, Optuna). Runs dans accidents_severity_dev, non enregistrés dans le registre.
3Se comparer à la productionChaque entraînement affiche un tableau des 4 métriques face au modèle @Production et un verdict « Send to prod ? » (même règle que le Trigger 3).
4Extraire le blueprintpython -m src.scripts.extract_blueprint <run_id> : tague le run export_to_prod=true et réécrit config/model_params.yml.
5ProposerPR de la branche DS vers main, contenant seulement le blueprint (la CI refuse de le mélanger avec du code).
6Production (Trigger 3)Après merge : réentraînement des 3 algorithmes avec le nouveau blueprint sur les données de production, règle du +0,01 en F1, gate GO/STOP. Si STOP ou échec des tests : le blueprint est automatiquement retiré de main — le blueprint en place reste toujours celui du modèle en production.

Production et développement : les différences

Production

  • Prefect, sur le VPS
  • Expérience accidents_severity_prod
  • 3 algorithmes, blueprint en vigueur
  • Modèles enregistrés dans le registre
  • Champion → gate → @Production

Développement

  • Poste du Data Scientist
  • Expérience accidents_severity_dev
  • Un algorithme, hyperparamètres libres
  • Non enregistrés (--no-register)
  • Meilleur run → blueprint → PR

Les deux partagent le même code d'entraînement (src/models/train_model.py), les mêmes données versionnées par DVC et les mêmes métriques : un résultat obtenu en développement est reproductible en production.

5 — MLflow : la trace de chaque entraînement et de chaque version

Serveur MLflow partagé sur le VPS (interface accessible par le VPN Tailscale, port 5001). Les métadonnées sont en base PostgreSQL, les modèles eux-mêmes dans le stockage objet MinIO.

Deux expériences : production et développement
ExpérienceContientAlimentée par
accidents_severity_prodLes entraînements officiels, 3 runs par cyclePrefect (Triggers 1 et 3, full-retrain)
accidents_severity_devLes explorations du Data ScientistPoste DS (MLFLOW_RUN_MODE=explore, par défaut)

Le développement est tracé et partagé au même titre que la production : chaque essai reste consultable et comparable par toute l'équipe.

Le registre des modèles et l'alias @Production
  • 3 modèles enregistrés — rf_accidents, xgb_accidents, lgbm_accidents — chacun gagne une version à chaque entraînement de production (v1, v2…).
  • Un seul alias @Production, toutes familles confondues : c'est lui que l'API et les Cockpits chargent. Promouvoir = déplacer l'alias puis redémarrer l'API : aucune image n'est reconstruite.
  • Chaque promotion pose un tag promoted_at : le Cockpit en déduit l'historique (Prod −1, Prod −2…), que MLflow ne conserve pas nativement.
