1 Découverte & téléchargement — download_task
src/data/import_raw_data.py — download_year() · resolve_year_urls() · discover_raw_files()
Résolution & téléchargement 6
Sous-étapeCe qui se passe
Résolution dynamique des URLsAPI data.gouv.fr interrogée à chaque run — aucun nom de fichier ni URL codé en dur, résiste aux changements de nommage côté ONISR
Filtrage des ressourcesFormat CSV uniquement, taille ≥ 500 Ko, exclusion des titres contenant "enrichi/consolidé/traitement/qualité/bilan/synthèse/analyse/open data/résumé" (datasets dérivés à écarter)
Matching par catégorie4 fichiers obligatoires (caractéristiques/lieux/usagers/véhicules) matchés par mot-clé sur le titre ; en cas d'ambiguïté, le titre le plus court est préféré (= fichier brut, pas une variante)
Téléchargement + nommage canoniqueSauvegardé sous {catégorie}-{année}.csv — nom imposé, indépendant du nom réel côté serveur ONISR (élimine par construction toute faute de frappe source, cf. incident 'carcteristiques' 2021/2022)
Validation immédiate post-téléchargement CRITICAL_validate_onisr_csv() : taille > 500 Ko, séparateur ; présent, colonnes obligatoires de la catégorie présentes — fichier supprimé et pipeline stoppé si un contrôle échoue
IdempotenceSi les 4 CSV sont déjà présents pour l'année, le téléchargement est sauté (pas de re-téléchargement inutile)
2 Validation Pandera — validate_task
src/data/schema_validator.py — load_and_validate_year() · 3 niveaux, sur les vraies données
Level 1 — Format 2
CheckCe qui est vérifié
Découverte fichier CRITICALLes 4 fichiers sont identifiables dans le dossier — fallback fuzzy (difflib, seuil 0.75) si le matching strict par mot-clé échoue, sinon CRITICAL
Lisibilité & non-vacuité CRITICALFichier non vide (taille > 0, ≥ 1 ligne après parsing), lisible avec un des séparateurs/encodages testés (;/,/tab × utf-8/latin-1/utf-8-sig)
Level 2 — Schéma 4
CheckCe qui est vérifié
Correctifs connus AUTO_CORRECTEDapply_known_fixes() — renommage Accident_Id→Num_Acc (ONISR 2022+) et nettoyage espaces insécables/superflus, appliqués avant toute validation
Colonnes obligatoires CRITICALToutes les colonnes requises de la catégorie présentes après correctifs, sinon pipeline stoppé
Colonnes inconnues WARNINGColonnes présentes mais absentes du schéma déclaré — signalées et ignorées, ne bloquent pas
Coercion de type Pandera AUTO_CORRECTED / WARNINGcoerce=True — colonne numérique lue en texte (artefact de formatage) reconvertie automatiquement ; si non convertible, WARNING (valeur conservée telle quelle)
Level 3 — Qualité 4
CheckCe qui est vérifié
Volumétrie WARNINGNombre d'accidents (table caractéristiques) hors des bornes attendues (QUALITY_BOUNDS) — données potentiellement tronquées
Taux de NaN WARNINGPar colonne, toutes tables — signalé si le taux dépasse le seuil configuré
Valeurs grav WARNINGTable usagers — valeurs hors {-1,1,2,3,4} signalées
Bornes lat/long WARNINGCoordonnées hors de la bounding box France métropolitaine signalées (n'empêche pas la suite)

Niveau global du rapport = le pire niveau rencontré (CRITICAL > WARNING > OK). CRITICAL lève une exception et stoppe le flow ; WARNING logue une alerte et laisse le pipeline continuer ; AUTO_CORRECTED est informatif (traité comme OK).

3 Synchronisation DVC — dvc_push_task / dvc_push_preprocessed_task
src/flows/etl_flow.py — _dvc_push_and_git_commit(), même mécanisme appelé 2 fois dans le flow (avant et après le preprocessing)
Données brutes — avant preprocessing 4
Sous-étapeCe qui se passe
Clone git jetableClone --depth 1 dans un dossier temporaire, détruit en fin d'exécution — aucune dépendance à un .git présent dans le conteneur
Copie + dvc addLes données réelles sont copiées dans le clone (pas de symlink — DVC les refuse), puis trackées
dvc push → Scaleway S3Upload vers le remote S3 — credentials écrites dans .dvc/config.local à partir des variables d'environnement (DVC n'interpole pas ${VAR} dans .dvc/config versionné)
Commit + push git [skip ci]Le .dvc mis à jour est commité et poussé sur origin/main — source de vérité partagée pour tout dvc pull ultérieur ; no-op silencieux si déjà à jour
Données préprocessées — après preprocessing 4

Même mécanisme que ci-dessus (clone jetable, dvc add/push, commit git [skip ci]), appliqué cette fois au dataset propre final (cumul_2021_2022_...) une fois l'étape 4 terminée — permet à tout consommateur (poste DS, VPS) de dvc pull le résultat exact de ce cycle sans rejouer tout le preprocessing.
