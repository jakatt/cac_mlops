Démo 1 — Un changement de code mis en production (Trigger 2)

Ce qu'elle prouve : le chemin complet d'un changement, du code à l'utilisateur, avec ses garde-fous — tests automatiques, relecture humaine, gate GO, tests après mise en ligne — et sa traçabilité dans GitHub, Prefect et Grafana.

scripts/demo/release.sh
Ce que fait le script
  • Crée une branche demo/release-… à partir de main, directement via l'API GitHub (le dépôt local n'est pas touché).
  • Change une seule ligne : docs/release.json, qui contient la date et l'heure du lancement.
  • Ouvre la PR et l'affiche dans le navigateur.

Pourquoi ce fichier : un fichier de docs/ ne reconstruit aucune image et ne redémarre aucun service — le déploiement est le plus court possible — et il n'est mis en ligne qu'au GO : la gate protège bien le changement. La date est affichée en bas de l'accueil des 3 Cockpits (« 🕒 Mise à jour du … »).

« Une ligne de code suit exactement le même chemin qu'une vraie évolution : tests, relecture, gate, mise en ligne, puis tests vus de l'utilisateur. Si un test échoue après le GO, la version précédente est restaurée automatiquement. »
Démo 2 — Déployer sur Kubernetes sans couper le service

Ce qu'elle prouve : une mise à jour sur Kubernetes remplace les pods un par un ; pendant toute l'opération, l'API et le Cockpit public continuent de répondre.

# Terminal 1 — le témoin scripts/demo/k8s.sh watch # Terminal 2 — l'action scripts/demo/k8s.sh deploy
Ce que font les commandes
  • watch interroge l'adresse publique kapsule.jakat-inc.fr deux fois par seconde — santé de l'API et du Cockpit public — et affiche le code de réponse de chacun. Ctrl-C affiche le bilan : réponses OK et en erreur.
  • deploy lance kubectl rollout restart sur l'API : exactement le mécanisme d'un vrai déploiement, puis attend la fin et affiche les nouveaux pods.
heure API Cockpit public 14:32:01 200 200 14:32:01 200 200 … Bilan : 240 réponses OK · 0 en erreur
Pourquoi il n'y a pas de coupure
  • 2 pods par service (en pratique sur les 2 machines du cluster).
  • Mise à jour progressive : un nouveau pod est créé, et l'ancien n'est arrêté qu'une fois le nouveau prêt (sonde /health réussie) — jamais moins de 2 pods en service.
  • Arrêt en douceur : un pod qui s'arrête continue de répondre 5 s, le temps que son retrait du service se propage — aucune requête n'arrive sur un pod déjà arrêté.

Dans Grafana (Accès · API · K8s) : la frise de disponibilité reste verte et le panneau « Pods api disponibles / demandés » montre le remplacement.

« Pendant que les pods sont remplacés, le témoin ne voit que des 200 : l'utilisateur ne s'aperçoit de rien. C'est ce qui se passe à chaque déploiement sur Kubernetes, sans aucune intervention. »
Démo 3 — Une panne de pod sans interruption

Ce qu'elle prouve : si un pod disparaît (plantage, machine perdue), le service continue sur l'autre pod et Kubernetes en recrée un automatiquement.

# Terminal 1 — le témoin (s'il n'est pas déjà lancé) scripts/demo/k8s.sh watch # Terminal 2 — la panne scripts/demo/k8s.sh kill
Ce que fait la commande
  • Choisit un pod API au hasard et le supprime (kubectl delete pod).
  • Affiche ensuite l'état des pods en direct : l'ancien passe à Terminating, un nouveau apparaît en ContainerCreating puis Running (~30 à 60 s). Ctrl-C pour arrêter le suivi.

Le Deployment Kubernetes impose « 2 pods API » : dès qu'il en manque un, il le recrée. Pendant ce temps, le second pod sert toutes les requêtes.

« Je viens de tuer un serveur en production. Le témoin reste à 200, et Kubernetes a déjà relancé un remplaçant : c'est l'auto-réparation. »
