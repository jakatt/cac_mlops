Flux MLOps — comment le système se protège tout seul

Trois façons pour une nouveauté d'arriver en production (données, code, nouveau modèle optimisé). Dans les trois cas, la même logique s'applique : des vérifications automatiques, un humain qui garde la main sur la décision finale, et un retour en arrière immédiat si quelque chose tourne mal. Le déploiement se fait toujours en deux temps : d'abord sur le VPS, puis — seulement si tout est OK — sur K8s (l'infrastructure parallèle, haute disponibilité et capable de monter en charge), jamais les deux à la fois. Sur K8s une mise à jour se fait sans interruption de service.

Validation humaine — une personne doit donner son accord Stop — le système s'arrête tout seul si un contrôle échoue Rollback — retour automatique à la version précédente Interruption — coupure de service réellement ressentie par un utilisateur Alerte — l'équipe est prévenue par email
ⓘ Règle simple à retenir : chaque Stop et chaque Rollback envoie automatiquement une Alerte — sauf les tests automatiques du code (Trigger 2 et 3), qui bloquent directement sur GitHub, visibles par l'équipe sans email séparé.

Le déroulé

Ce qui se passe, dans l'ordre — VPS d'abord, K8s ensuite si tout est OK :

  • Si la source de données officielle est injoignable ou le fichier manquant → Stop, une Alerte prévient l'équipe.
  • Avant de bloquer quoi que ce soit, le système essaie d'abord de corriger tout seul les petits problèmes déjà rencontrés par le passé (colonne renommée, espace superflu, format de nombre, nom de fichier légèrement différent...) — en coulisses, sans alerte ni interruption.
  • Si malgré cette correction automatique un problème grave subsiste (colonnes, volumes, format) → Stop + Alerte.
  • Le modèle se réentraîne. Si aucune des nouvelles versions ne fait mieux que celle déjà en place → Stop + Alerte : rien ne change, la production continue avec l'ancien modèle.
  • Juste avant de présenter les résultats à un humain, une dernière vérification de bon fonctionnement du serveur a lieu. Si elle échoue → Stop + Alerte.
  • Validation humaine : les résultats du nouveau modèle sont présentés dans le Cockpit. Rien n'est encore appliqué — un humain donne le feu vert ou annule.
  • Le feu vert donné, le nouveau modèle est mis en service d'abord sur le VPS : une Interruption d'environ 30 secondes a lieu le temps du redémarrage.
  • Si la vérification qui suit sur le VPS échoue → Rollback vers la version précédente + Alerte — et le déploiement s'arrête là, K8s n'est jamais touché.
  • Seulement si le VPS est OK, la même mise à jour est ensuite déployée sur K8s (infrastructure parallèle, haute disponibilité) — sans aucune interruption de service : l'ancienne version continue de répondre aux utilisateurs tant que la nouvelle n'est pas vérifiée. Deux vérifications indépendantes y sont refaites (le déploiement lui-même, puis son bon fonctionnement) ; si l'une échoue → 2 rollbacks possibles (un par vérification) + 2 alertes, le VPS reste inchangé.

Ce qui se passe, dans l'ordre — VPS d'abord, K8s ensuite si tout est OK :

  • Si les tests automatiques du nouveau code échouent → Stop : la fusion est bloquée directement sur GitHub, visible par l'équipe sans email séparé.
  • Validation humaine n°1 : un responsable relit et valide le code — avant même que quoi que ce soit ne soit préparé pour la mise en ligne.
  • Si une faille de sécurité grave est détectée dans la nouvelle version → Stop + Alerte, rien n'est touché sur le VPS.
  • Juste avant la mise à jour, une dernière vérification de bon fonctionnement a lieu sur le VPS. Si elle échoue → Stop + Alerte.

Ce qui se passe, dans l'ordre — VPS d'abord, K8s ensuite si tout est OK :

  • Si les tests automatiques échouent → Stop : la proposition n'est pas retenue, bloquée directement sur GitHub, sans email séparé.
  • Validation humaine n°1 : un responsable relit et valide la proposition — avant même que le réentraînement ne démarre.
  • Le modèle se réentraîne avec les nouveaux réglages. Si aucun des candidats ne fait mieux que le modèle actuel → Stop + Alerte : rien ne change en production.
  • Juste avant de présenter les résultats, une dernière vérification de bon fonctionnement du serveur a lieu. Si elle échoue → Stop + Alerte.
  • Validation humaine n°2 : les résultats sont présentés dans le Cockpit. Rien n'est encore appliqué — un humain donne le feu vert ou annule.
  • Le feu vert donné, le nouveau modèle est mis en service d'abord sur le VPS : une Interruption d'environ 30 secondes a lieu le temps de la mise en service.
  • Si une vérification après la mise en service sur le VPS échoue → Rollback vers l'ancienne version + Alerte — le déploiement s'arrête là, K8s n'est jamais touché.

☉

Pourquoi K8s vient toujours après, jamais en même temps : tant que le VPS n'a pas prouvé que la nouveauté fonctionne, rien n'est envoyé sur K8s — c'est un deuxième filet de sécurité, pas une simple copie. Sur K8s, un déploiement ne coupe jamais le service : la nouvelle version est vérifiée en coulisses pendant que l'ancienne continue de répondre, et ne la remplace qu'une fois prête — c'est ce qui permet à un retour en arrière de s'y produire sans qu'aucun utilisateur ne le remarque.
