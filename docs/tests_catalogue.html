③ Prefect Après le GO — tests fonctionnels 8

Après le GO, Prefect se comporte comme un utilisateur : il appelle l'API et clique dans chaque onglet du Cockpit public, puis vérifie la réponse. Ces tests vérifient que ça marche, jamais que le modèle a raison (c'est le rôle de son évaluation à l'entraînement). Au premier échec : retour automatique à la version précédente + alerte.

Comment ils s'exécutent — interne puis externe, VPS puis Kubernetes
PassageAdresse appeléeQuestion posée
1. InterneLe réseau du serveur (Docker sur le VPS, réseau du cluster sur K8s)L'application fonctionne-t-elle ?
2. ExterneL'adresse publique HTTPS (mlops.jakat-inc.fr, kapsule.jakat-inc.fr)L'utilisateur peut-il y accéder ? (nom de domaine, certificat, Caddy, load balancer)

L'externe ne tourne que si l'interne a réussi : un échec désigne donc directement la cause. Ordre : API interne → API externe → Cockpit public interne → Cockpit public externe.

Anti-abus de l'API — à la demande, test-rate-limit 5

Cockpit → Orchestration → « Tester la protection anti-abus sur l'API » (~5 s), jamais pendant un déploiement. Vérifie les 2 limites de nginx sur les prédictions : par client (20/min, rafale 10) et globale (60/min, rafale 30).

5Limite globale — plusieurs clients sous leur quotaDes clients raisonnables finissent bloqués (429) : la charge totale est plafonnée

Le Cockpit public n'est pas concerné : il calcule ses prédictions lui-même, sans passer par l'API. Après le test, le quota global reste épuisé ~15 s.
