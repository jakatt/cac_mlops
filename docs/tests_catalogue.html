PREFECT Tests fonctionnels — la solution marche-t-elle pour l'utilisateur ?
Après chaque déploiement, Prefect se comporte comme un utilisateur : il se connecte, demande une vraie prédiction et vérifie la réponse — sur chaque accès, sur le VPS puis sur Kubernetes. Au premier test en échec : retour automatique à la version précédente + alerte.

2 · Interne puis externe : deux questions différentes

PassageAdresse appeléeQuestion posée
1. InterneDirectement dans le réseau du serveur (nginx du VPS, service interne K8s)L'application fonctionne-t-elle ?
2. ExterneL'adresse publique HTTPS, comme un vrai utilisateurL'utilisateur peut-il y accéder ? (nom de domaine, certificat TLS, reverse-proxy Caddy, load balancer)

L'externe n'est lancé que si l'interne réussit : un échec indique donc directement la cause — l'application elle-même, ou seulement le chemin d'accès public. Ordre sur chaque environnement : API interne → API externe → Cockpit public interne → Cockpit public externe.

5 · Test fonctionnel anti-abus — à la demande

Cockpit → Orchestration → « Tester la protection anti-abus sur l'API » (test-rate-limit, ~5 s) — jamais pendant un déploiement. Vérifie les 2 niveaux de limite de nginx sur les prédictions de l'API : par client (20/min, rafale 10) et globale (60/min, rafale 30). Plusieurs clients sont simulés depuis le réseau interne (IP fictives) ; depuis Internet, impossible de se faire passer pour un autre client.
